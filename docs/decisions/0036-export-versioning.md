## 背景

ADR-0026・ADR-0030 まででエクスポート形式は
`{ positions, settings, history }` だが、バージョン情報が無かった。将来形式が
変わったときに、古いリーダーが新しいファイルを誤って取り込み、
読書位置や履歴を壊す恐れがある（ADR-0030・ADR-0032 の未決定
「エクスポート形式のバージョニング」）。

## 決定

### エクスポート

- 出力 JSON のトップレベルに `"version": 1` を付与する。
- 既存の `positions` / `settings` / `history` はそのまま維持する。

### インポート

- `version` が無い JSON（旧形式）は従来どおり取り込む（後方互換）。
- `version` が 1 の JSON は従来どおり取り込む。
- `version` が 1 以外（未知のバージョン）の JSON は拒否し、
  状態メッセージ（`Unsupported export version: N.`）で理由を表示する。
  何も取り込まない（fail-closed）。
- バージョンの判定は localStorage への書き込みより前に実行するため、
  拒否されたファイルで既存データが壊れることはない。

## 選択肢と根拠

| 選択肢 | 判断 |
| --- | --- |
| バージョン付与＋未知は拒否（採用） | 新しい形式を古いリーダーが誤って読む事故を防げる |
| バージョンを付けるが検証しない | 事故を防げない |
| 未知のバージョンも受け付ける | フィールド欠落時にデータが壊れる |

## 影響

- 新しくエクスポートしたファイルには `version: 1` が入る。
- 旧形式（version なし）のバックアップも引き続きインポートできる。
- 将来形式を変えるときは `EXPORT_VERSION` を上げ、古い形式の読み取り
  処理を追加する必要がある。
- 追加依存は無く、既存の `web-sys` 機能の範囲で実装している。

## 検証

- ヘッドレス Chrome 157 と `tools/verify-web-reader.py` の E2E 138 項目が
  3 回連続で成功。`version: 1` のインポート成功、未知のバージョン
  （999）の拒否と既存データが壊れないことを確認した。旧形式の互換性は
  既存の E2E（設定・履歴のインポート）で確認済み。
- `cargo test --all-targets --locked` は 119 件成功。
- 6 ゲート（fmt / check / test / clippy / wasm32 × 2）と `trunk build` が成功。
- CI は billing issue で実行不可（ローカル検証で代替）。
