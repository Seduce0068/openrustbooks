## 現状

R6 R1-archive#3 として、ZIP / EPUB の入力パスが扱う深さ（コンポーネント数）に
上限が無いことを監査した。

### 深さ制限の欠如

- `core/src/archive.rs:380-433` の `normalize_path()` は、`\` を `/` へ寄せ、
  先頭の `./` を除去し、`..` と絶対パス／ドライブ文字を拒否した後、
  `components: Vec<&str>` へ `push` して `join("/")` する。
  `components` の長さを検査する処理は無く、深さは入力長に比例する。
- `core/src/epub.rs:766-806` の `resolve_reference()` も同様に
  `components: Vec<&str>` を伸長させ、`pop()` で `..` をさかのぼるだけで、
  深さの上限を持たない。
- 両者は再帰呼び出しを伴わず、反復文と `Vec` のヒープ確保のみで動作する。
  スタック深さは入力に比例しない。

### 既存の防御

- 入力バイト列: `DEFAULT_MAX_READ_BYTES = 256 * 1024 * 1024`（`core/src/io.rs:12`）。
- ZIP エントリ名（`normalize_path()` が受け取る raw 名）: ZIP 仕様の命名長
  フィールドが u16（最大 65,535 バイト）であることに基づき、1 エントリの
  パス長が実質的に限定される。出典は「仕様末尾の命名長フィールドに基づく
  一般知識だがローカルに一次資料なし（推測）」であり、一次資料で未確認。
- XML 内容の参照（`resolve_reference()` が受け取る href）: ZIP 名の u16 長は
  適用されない。href は OPF 等のエントリ内容に含まれる文字列であり、
  `max_entry_size = 64 MiB`（1 エントリの非圧縮サイズ上限）が実質的な上限になる。
- `ArchiveLimits`（`core/src/archive.rs:36-52`）: `max_entries = 4096`、
  `max_entry_size = 64 MiB`、`max_total_size = 256 MiB`。
- 実展開サイズ: `expanded: AtomicU64` のセッション予算（`core/src/archive.rs:86`、
  ADR-0251）。
- パス検証は fail-closed（ADR-0004 / 0013 / 0240）で、脱出・スキーム付き URL・
  正規化後同名は拒否される。

## 決定

深さ上限（`max_path_components` 等）を追加しない。現状の設計を受容し、
上記の防御との責任分界をここに記録して R1-archive#3 を完了とする。

理由は次のとおり。

- 正規化と参照解決は非再帰であり、深さによるスタック消費の経路が無い。
- メモリ確保は入力長に比例する。ZIP エントリ名は 256 MiB の読取上限と
  上記 u16 長（推測を含む一般知識）で、XML の href は 256 MiB の読取上限と
  64 MiB per entry（`max_entry_size`）で、それぞれ実質的に抑えられている。
  u16 長を `resolve_reference()` 側へ適用しないことに注意。
- 4096 entries / 64 MiB per entry / 256 MiB total に加え、
  実展開の `AtomicU64` 予算が、深さに伴う総量の増加を既に制限する。
- fail-closed のパス検証が脱出を拒否するため、深さそのものが
  新たな信頼境界を生まない。
- サニタイザには深さ制限を避けた前例がある（ADR-0050 / 0065）が、
  これらは 1000 / 10000 階層の回帰テストを併せて追加している点が異なる。
  本件は回帰テストを伴わないため同じ方針をそのまま適用できず、
  wasm 環境での深いパスによる DoS の実測（未決定）を残す。

## 選択肢と根拠

| 選択肢 | 判断 |
| --- | --- |
| 深さ上限を追加せず設計受容（採用） | 非再帰・有限入力・既存の多重防御で十分。API と契約を変えない |
| `ArchiveLimits` に `max_path_components` を追加 | 実装時に選ぶなら望ましい。既存の limits 契約へ統合でき、呼び出し側の設定も一箇所。ただし今回は出典のある上限値が無いため追加しない |
| `normalize_path` に引数を追加 | 内部ヘルパーのシグネチャ変更が全呼び出し側へ波及し、`resolve_reference` 側との不整合が残る |
| 見送り放置 | 判断と責任分界が記録されず、TODO が再浮上するため採らない |

数値 `128` は比較のための**例示値**であり、出典は無い。
実装時に上限を導入する場合も、この値を根拠として扱ってはならない。
出典のない数値は例示として扱い、決定の根拠にしない。本 ADR はこの運用を
他 ADR へ委ねず、ここで直接明記する。
また、この `128` は ADR-0188 / 0209 の atomic write 一時ファイル作成の
再試行回数（最大 128 回）とは無関係である。値の一致は偶然であり、
本件の上限候補の根拠へ転用してはならない。

## 根拠

- ADR-0004: ZIP を core の読み取り専用モジュールとして実装し、
  パス逸脱と過大展開への対策を記録した起点。
- ADR-0013: EPUB 表示経路の fail-closed 化とサイズ上限。
- ADR-0050 / 0065: 深さ制限を避けた前例。ただし 1000 / 10000 階層の
  回帰テストを伴う点で本件と異なる（本件はテスト追加なし）。
- ADR-0240: 正規化後同名エントリの fail-closed 拒否。
- ADR-0251: 実展開サイズの `AtomicU64` セッション予算。

## 影響

- コード・API・E2E は変更しない。`ArchiveLimits` のフィールドも増やさない。
- `normalize_path()` と `resolve_reference()` の現在の契約（失敗時は
  `CoreError::Validation` / `CoreError::Archive`）は不変。
- 深さそのものは拒否しないが、脱出・空パス・スキームは従来どおり拒否する。
- R1-archive#3 は「設計受容」として完了へ移動し、
  以下の未決定は追跡事項として残す。

## 未決定

- 上限値の出典（`128` は例示値にすぎず、実測・仕様根拠が無い）。
- JS DTO（`WasmArchive` 等）を信頼境界とみなすかどうか。
- XML / TOC の深さ（ADR-0006 の平坦リスト）との一本化要否。
- 完全一致 raw 名の検出方針（ADR-0240 の未決定を継承）。
- wasm 環境での深いパスによる DoS の実測（現状は推論のみ）。
